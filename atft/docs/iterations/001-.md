# Iteration 001 — Record a vaccination tutorial

Status: Complete draft for user review. Product choices below are agreed; detailed fixtures, exercises, and technical defaults await final review. Do not begin implementation as part of this specification task.

## Purpose and audience

Build the first complete learning journey for the API test framework tutorial described in `atft/docs/vision.md`. The learner has coding experience but is new to API test automation. An IDE-style web application explains and demonstrates each concept, then lets the learner complete targeted gaps in editable starter code.

## Agreed decisions

- Teach recording a new vaccination for a fictional patient using a FHIR REST API.
- Cover one complete test: Gherkin feature, C# Reqnroll step definitions, and request/response models.
- Teach C# HttpClient with Reqnroll. Selenium is excluded; this supersedes its inclusion in the vision for this iteration.
- Provide a separate worked example alongside the learner's exercises.
- Simulate the entire test. Never compile or execute learner-authored code or send the tutorial's clinical requests to a real API.
- Explain mistakes and provide a way to reveal a solution.
- Use base FHIR R4 (4.0.1).
- Include one successful creation scenario. API failure scenarios are outside iteration 001; incorrect learner submissions still receive instructional feedback.
- Use small C# classes containing the fields needed for the tutorial, explicitly described as a teaching subset rather than complete FHIR models. Do not use a FHIR SDK for the lesson.
- Save learner code and completed steps locally in the browser so progress survives refresh. Include a Start over action. No user accounts in iteration 001.
- Build the application with React, TypeScript, and Vite. Run the tutorial entirely in the browser with a desktop-first layout; C# is the language taught, not the application implementation language.
- Only targeted gaps in starter code are editable. Surrounding code is read-only. Validate predefined answers while accepting harmless formatting differences; give specific feedback for each gap without executing C#.
- Show solution displays the answer alongside the editor. It does not automatically replace learner input; learners apply the answer and check their work.
- Unlock lessons sequentially after successful checks. Previously unlocked lessons remain available. Editing a passed answer invalidates that lesson's pass and prevents the final simulation until it passes again.
- Use a separate worked vaccination example with different fictional data.
- Offer Run simulated test after all exercises pass. Display assembled code, illustrative HTTP request/response, passing Given/When/Then results, and a learning recap.

## Agreed lesson sequence

1. Understand the API: inspect a fictional patient, vaccination request, and expected response.
2. Describe the behavior: complete a Gherkin scenario.
3. Model the data: complete small C# classes mapping to FHIR JSON.
4. Build the request: complete Reqnroll bindings that prepare and send an HttpClient request (illustrated only; never executed by the application).
5. Verify the response: complete status and returned-data assertions, then view a simulated test result.

Each coding stage includes an explanation, a separate worked example, starter code, Check my work, and Show solution.

## FHIR contract — details proposed for review

- Pin the tutorial to base FHIR R4 (4.0.1), with no jurisdiction-specific implementation guide.
- Model a completed vaccination using the Immunization resource.
- Teach `POST [base]/Immunization`; identify the existing fictional patient using `patient.reference` in the resource rather than a nested patient URL.
- Include `resourceType`, `status`, `vaccineCode`, `patient`, `occurrenceDateTime`, and `lotNumber`. Use `vaccineCode.text` for this base-R4 teaching example; terminology coding and national profiles are outside scope. Explain that real integrations may require coded values.
- Request and return FHIR JSON (`application/fhir+json`), with `Prefer: return=representation`.
- Simulate `201 Created`, a Location header, and an Immunization response with a server-assigned ID.
- Clearly distinguish the educational subset and predefined checks from a full FHIR validator or functioning clinical system.

- [FHIR R4 REST interactions](https://hl7.org/fhir/R4/http.html)

### Lesson 3: Model the data

Explain C# properties, JSON property names, nested objects, and using the same teaching model for request and response. Explain why the nullable ID is omitted on creation. A date string is intentionally used to preserve the fixture's date-only FHIR representation; these classes do not validate arbitrary FHIR dates or resources. File `Immunization.cs`:

```csharp
using System.Text.Json.Serialization;

public sealed class Immunization
{
    [JsonPropertyName("resourceType")]
    public string ResourceType { get; set; } = "Immunization";

    [JsonPropertyName("id")]
    [JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]
    public string? Id { get; set; }

    [JsonPropertyName("status")]
    public string Status { get; set; } = "completed";

    [JsonPropertyName("vaccineCode")]
    public CodeableConcept VaccineCode { get; set; } = new();

    [JsonPropertyName("patient")]
    public PatientReference Patient { get; set; } = new();

    [JsonPropertyName("occurrenceDateTime")]
    public string OccurrenceDateTime { get; set; } = "";

    [JsonPropertyName("lotNumber")]
    public string LotNumber { get; set; } = "";
}

public sealed class CodeableConcept
{
    [JsonPropertyName("text")]
    public string Text { get; set; } = "";
}

public sealed class PatientReference
{
    [JsonPropertyName("reference")]
    public string Reference { get; set; } = "";
}
```

### Lessons 4 and 5: Bindings, request, and assertions

Lesson 4 explains `[Binding]`, step attributes, a captured string parameter, per-scenario fields, serialization, HTTP headers, and awaiting an HTTP response. Lesson 5 explains deserialization, checking status separately from data, and why an assertion detects a mismatch. Use NUnit constraint assertions as the teaching syntax. Explain that Reqnroll connects Gherkin to C#, HttpClient handles HTTP, System.Text.Json maps JSON, and NUnit supplies assertions. These are displayed educational code, not browser dependencies.

File `RecordVaccinationSteps.cs` (one shared file, with lesson 4 editing Given/When gaps and lesson 5 editing Then gaps):

```csharp
using System;
using System.Net.Http;
using System.Net.Http.Headers;
using System.Text;
using System.Text.Json;
using System.Threading.Tasks;
using NUnit.Framework;
using Reqnroll;

[Binding]
public sealed class RecordVaccinationSteps
{
    private static readonly HttpClient Client = new()
    {
        BaseAddress = new Uri("https://fhir.example.test/")
    };
    private Immunization _request = null!;
    private HttpResponseMessage _response = null!;

    [Given("a vaccination for patient {string}")]
    public void GivenAVaccination(string patientReference)
    {
        _request = new Immunization
        {
            Status = "completed",
            Patient = new PatientReference { Reference = patientReference },
            VaccineCode = new CodeableConcept { Text = "Influenza vaccine" },
            OccurrenceDateTime = "2026-01-15",
            LotNumber = "TRAINING-FLU-001"
        };
    }

    [When("I submit the vaccination")]
    public async Task WhenISubmitTheVaccination()
    {
        using var message = new HttpRequestMessage(HttpMethod.Post, "Immunization");
        message.Headers.Accept.Add(new MediaTypeWithQualityHeaderValue("application/fhir+json"));
        message.Headers.Add("Prefer", "return=representation");
        message.Content = new StringContent(
            JsonSerializer.Serialize(_request), Encoding.UTF8, "application/fhir+json");
        _response = await Client.SendAsync(message);
    }

    [Then("the response status is {int}")]
    public void ThenTheResponseStatusIs(int expectedStatus)
    {
        Assert.That((int)_response.StatusCode, Is.EqualTo(expectedStatus));
    }

    [Then("the recorded vaccination matches the request")]
    public async Task ThenTheRecordedVaccinationMatches()
    {
        var json = await _response.Content.ReadAsStringAsync();
        var actual = JsonSerializer.Deserialize<Immunization>(json)
            ?? throw new InvalidOperationException("Expected an Immunization response.");
        Assert.That(actual.Id, Is.Not.Null.And.Not.Empty);
        Assert.That(actual.ResourceType, Is.EqualTo("Immunization"));
        Assert.That(actual.Status, Is.EqualTo(_request.Status));
        Assert.That(actual.Patient.Reference, Is.EqualTo(_request.Patient.Reference));
        Assert.That(actual.VaccineCode.Text, Is.EqualTo(_request.VaccineCode.Text));
        Assert.That(actual.OccurrenceDateTime, Is.EqualTo(_request.OccurrenceDateTime));
        Assert.That(actual.LotNumber, Is.EqualTo(_request.LotNumber));
    }

    [AfterScenario]
    public void Cleanup() => _response?.Dispose();
}
```

The completed files form a coherent teaching example; no .NET project, package restore, or execution environment is part of the learner app. Label the assembled code as tutorial files, not a downloadable runnable project.

### Exact editable gaps and feedback

String-content gaps exclude their surrounding quotes. Token gaps exclude surrounding punctuation. Each prompt states whether a string value or a C# token is expected. The table's guidance is the feedback for an incorrect answer; empty gaps instead say “Enter a value for [label].” Do not reveal the exact answer in generic incorrect feedback.

| Gap ID | Location / label | Accepted answer | Incorrect-answer guidance |
| --- | --- | --- | --- |
| feature.given | First step keyword | `Given` | Use the keyword that establishes the scenario's starting context. |
| feature.patient | Patient reference inside quotes | `Patient/patient-001` | Use the exercise patient reference, including the resource type. |
| feature.when | Submission step keyword | `When` | Use the keyword that describes the action under test. |
| feature.then | Status step keyword | `Then` | Use the keyword that introduces an expected outcome. |
| feature.status | Expected HTTP status | `201` | Check the API contract's successful creation status. |
| model.vaccine | Type of VaccineCode property | `CodeableConcept` | The vaccine is represented by a nested concept object. |
| model.patient | Type of Patient property | `PatientReference` | Use the teaching class that contains a patient reference. |
| model.date | JsonPropertyName value for OccurrenceDateTime | `occurrenceDateTime` | Match the administration-date property in the JSON fixture, including case. |
| request.status | Status initializer in Given | `completed` | Describe a vaccination that has already been administered. |
| request.patient | Reference initializer in Given | `patientReference` | Use the parameter captured from the Gherkin step. |
| request.method | Member following HttpMethod. | `Post` | Choose the HTTP method used to create the resource. |
| request.endpoint | Relative request URL | `Immunization` | Send the request to the resource collection in the contract. |
| request.media | Third StringContent argument's string content | `application/fhir+json` | Use the FHIR JSON media type. |
| response.status | EqualTo argument in status assertion | `expectedStatus` | Compare with the status passed from the scenario. |
| response.model | Deserialize generic type | `Immunization` | Deserialize into the resource model you completed. |
| response.patient | EqualTo argument for patient assertion | `_request.Patient.Reference` | Compare the returned patient reference with the submitted reference. |
| response.lot | EqualTo argument for lot assertion | `_request.LotNumber` | Compare the returned lot number with the submitted lot number. |
